## 2. Архитектура всей системы

Система реализует федеративное прогнозирование временных рядов в двух режимах:

- централизованные server-side агрегаторы (например, FedAvg, Krum, weighted median);
- децентрализованные peer-to-peer протоколы синхронизации (LVP и аналоги) по графу соседства между агентами.

На каждом раунде клиент обучает локальную модель на своей локальной серии, затем отправляет параметры (или их атакованную версию при Byzantine-сценарии), после чего выполняется выбранная процедура синхронизации.

## 3. Данные и формирование клиентских задач

### 3.1 Источники данных

Базовый временной слой формируется из MCC-транзакций (файлы в 01_data_transactions). Основной файл для полного режима: dat_mcc_full.csv.

Экзогенный слой включает внешние информационные каналы:

- новостной сигнал Fontanka;
- Reuters daily sentiment (при наличии в контуре интеграции).

Экзогенные ряды выравниваются по общей временной оси и прикрепляются ко всем клиентам одинаково.

### 3.2 Разбиение между агентами

В текущем сценарии используется column_partition = contiguous:

- MCC-колонки делятся на последовательные блоки;
- каждому клиенту назначается свой блок;
- локальная целевая серия клиента получается как агрегирование его блока.

Итог: клиенты имеют общую временную ось, но разные наблюдаемые подмножества признаков, что и создает управляемую гетерогенность.

### 3.3 Информационные профили

Для построения графа соседства каждому клиенту формируется информационный профиль (set-like представление):

- теги домена/источника;
- дискретизированные статистики локальной серии;
- признаки по MCC-группам/бакетам;
- модальные теги экзогенных каналов.

Именно эти профили используются для Jaccard-подобной топологии.

## 4. Модели в системе

В репозитории поддерживаются интерпретируемые параметрические модели:

- DynamicLinearModel;
- ARMAXModel;
- KalmanFilterModel;
- StructuralTimeSeriesModel;
- MarkovSwitchingRegressionModel (доступна, но не входит в финальный фиксированный прогон текущего пакета).

В текущем сравнительном прогоне по моделям использованы первые четыре.

## 5. Полный цикл одного раунда эксперимента

Для каждого клиента i в раунде t:

1. Формируется локальный train/test split.
2. Локальная модель дообучается local_epochs шагов.
3. Получаются параметры theta_local_i^t и локальные метрики MAE/sMAPE.
4. Если клиент malicious, к передаваемым параметрам применяется corrupt_params(...).
5. По выбранному агрегатору/протоколу строится новое состояние theta_i^{t+1}.
6. В history пишутся network_mae, network_smape и диагностические величины синхронизации.

## 6. Byzantine-атаки и их смысл

Реализованные стратегии (aggregators.py):

- label_flip: инверсия знака параметров + шум;
- noise: гауссов шум;
- noise_colluded: шум + согласованный bias по ключам параметров;
- noise_heavy_tail: тяжелые хвосты (Student-t);
- noise_colluded_heavy_tail: colluded bias + тяжелые хвосты;
- random: замена на случайные значения в широком диапазоне.

В текущем сценарии используется noise_colluded. Эта атака особенно важна для анализа робастности, поскольку независимый шум частично усредняется, но согласованный сдвиг между malicious-клиентами сохраняется и проходит в агрегирование.

## 7. Механика LVP

### 7.1 Обновление состояния

В коде используется форма:

$$
\theta_i^{t+1}=(1-\gamma)\left[\theta_i^t+\alpha\sum_{j\in N_i(t)}b_{ij}^t\left(\theta_j^{sent,t}-\theta_i^t\right)\right]+\gamma\theta_i^t,
$$

где:

- alpha: интенсивность межагентного согласования;
- gamma = self_weight: демпфирование и возврат к собственной траектории;
- theta_j^{sent,t}: именно переданные параметры j (могут быть уже corrupted);
- b_ij^t: доверительные веса ребер.

### 7.2 self_weight: физический смысл

self_weight задает долю «инерции» локальной модели после шага согласования:

- self_weight = 0: максимальная восприимчивость к консенсусному шагу;
- self_weight > 0: частичное сохранение локального состояния, меньшая амплитуда колебаний.

В текущем пакете по multiseed tuning лучшим оказался self_weight = 0.0.

## 8. Граф соседства и гибридный Жаккар

### 8.1 Базовый Jaccard

Для профилей S_i и S_j:

$$
\kappa_{ij}^{(J)}=\frac{|S_i\cap S_j|}{|S_i\cup S_j|}.
$$

Ребро формируется при условии kappa_ij >= tau.

### 8.2 Гибридный режим jaccard_cosine_hybrid

Если выбран similarity_mode = jaccard_cosine_hybrid, используется выпуклая смесь структурного сходства и сходства направлений параметрических дельт:

$$
\kappa_{ij}^{(H)}=\lambda\,\kappa_{ij}^{(J)}+(1-\lambda)\,\frac{1+\cos(\Delta_i,\Delta_j)}{2},
$$

где:

- Delta_i = theta_local_i^t - theta_prev_i^{t-1};
- cos(...) сначала считается в [-1,1], затем переводится в [0,1];
- lambda = lambda_jaccard в [0,1].

Дополнительно действует фильтр tau_cos_min: если cos(Delta_i, Delta_j) < tau_cos_min, ребро отбрасывается даже при высоком гибридном score.

Практический смысл:

- Jaccard учитывает совместимость по данным/профилям;
- cosine(deltas) учитывает совместимость по текущему направлению обучения;
- смесь снижает риск «слепого» согласования между агентами, которые структурно похожи, но двигаются в противофазе.

## 9. Как именно считается мера согласованности на L2-норме

В текущем раннере логируются поля:

- sync_component_l2_mean;
- sync_component_l2_max.

Алгоритм:

1. По направленному neighbor-graph строится неориентированное компонентное разбиение.
2. Для каждого клиента i считается L2-дистанция между состоянием после синхронизации текущего раунда и состоянием до этой синхронизации:

$$
d_i^t=\left\|\theta_i^{t,after\_sync}-\theta_i^{t,before\_sync}\right\|_2.
$$

3. Внутри каждой компоненты берется среднее по клиентам.
4. sync_component_l2_mean = среднее по компонентам этих средних.
5. sync_component_l2_max = максимум d_i^t по всем клиентам компонент.

Важная деталь реализации: дистанция считается только по общим числовым ключам параметров одинаковой формы. Если ключи не пересекаются или формы несовместимы, вклад пропускается.

Интерпретация:

- высокая sync_component_l2_mean означает, что раунд синхронизации сильно сдвинул локальные модели;
- низкая величина означает мягкое/стабилизированное межклиентское влияние;
- метрика описывает «амплитуду синхросдвига», а не напрямую качество прогноза.

## 14. Почему абляции иногда «не сходятся» с финальными параметрами

Это ожидаемо и методологически объяснимо.

### 14.1 Разные целевые функции

В одном месте оптимизируется минимум single-sweep финальной MAE, в другом месте используется multiseed objective = mean + 0.5*std. Эти критерии не обязаны давать один и тот же argmin.

### 14.2 Разная степень усреднения по seed

Single-seed минимум может быть случайно удачным. Multiseed-оптимум более стабилен и обычно предпочтительнее для публикационного выбора.

### 14.3 Связанность гиперпараметров

Параметры tau, alpha, self_weight и similarity_mode связаны. Оптимум alpha при фиксированном tau может смещаться при другом tau. Поэтому частные одномерные срезы не всегда совпадают с joint-настройкой.

### 14.4 Нелинейность динамики в присутствии Byzantine-искажений

Colluded-атаки могут изменять эффективную геометрию параметрического пространства между раундами. Локальные минимумы по ошибке становятся более «шумными» и менее переносимыми между seed.

### 14.5 Proxy-оценка против refit-оценки

В текущем пакете используется network_eval_mode = proxy. Это ускоряет большие sweep, но может немного отличаться от полной post-sync refit-оценки. Различие метрик может слегка переставлять ранги близких гиперпараметров.

### 14.6 Конечный бюджет раундов

Оптимум по 10 раундам не обязан совпадать с оптимумом по длинному горизонту. Некоторые параметры ускоряют раннее снижение ошибки, но проигрывают на длинном рантайме, и наоборот.

## 16. Ограничения и риски интерпретации

- Часть выводов о «победе» методов отличается между single-seed и multiseed режимами.
- При очень малых разницах MAE (единицы-десятки) практически важнее устойчивость и воспроизводимость, чем формальный top-1.
- Результаты на текущем horizon/round budget могут быть не полностью переносимы на более длинные раны.
